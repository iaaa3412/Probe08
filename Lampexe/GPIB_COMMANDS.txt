  The FET1/FET2/Relay1-5 cards' generic "SWITCHBOX" IDN, cross-referenced
  against the real Agilent/HP 75000-series VXI catalog, matches two specific,
  well-documented product families:
    - E1345A "16-Channel Relay Multiplexer" - reed-relay based, programmable
      as one 1x16 3-wire mux, two 1x8 3-wire muxes, or a 1x8 6-wire mux.
    - E1351A "16-Channel FET Multiplexer" - same 1-of-N channel-selection
      concept, FET-switched for faster scanning, typically paired with a
      scanning DMM (matches FET1's own row-18 description, "Switch Voltage
      Measurement Points", i.e. routing signal to InternalDMM).

  does make a true crosspoint product in the same 75000/VXI family - E1465A/

  grid - but nothing in either scanned table identifies as one of those; every
  relay/FET card reports the generic multiplexer-family "SWITCHBOX" string.
  Conclusion: this relay subsystem is NOT a crosspoint matrix. It's several
  simple multiplexer cards CASCADED together - consistent with "Relay1 selects
  PS as Relay5's input" (stage 1 picks a source, feeds it to stage 2, which
  routes it further), which is the signature of chained multiplexers, not a
  single-step "any input to any output" crosspoint operation.

  Sources (web search, 2026-07-22): Keysight/Agilent E1301A datasheet and

1. HOW COMMANDS ARE SENT (sub_41ca40, binaryninja.txt:14849)
======================================================================
Every GPIB command in the app goes through one shared helper, sub_41ca40(arg1, arg2, arg3):

  - arg1 is an instrument key ("2001X", "Relay1", "Keithley2400"). The helper
    builds the real control name by prepending "HPIB_" to it
    (__vbaStrCat(*arg1, u"HPIB_") - line 14908), giving "HPIB_2001X" etc.
  - It then LATE-BINDS to that control by name (__vbaLateIdCallLd against the
    form's Controls collection) rather than using a hardcoded object reference -
    so all 3 instruments share this exact same send/retry logic.
  - The command string itself (arg2) is sent via that control's
    .Output(<command string>) method (line 14966: u"Output") - "Output" is the
    classic HP-BASIC-style GPIB write call the Agt3494A control exposes.
  - Runs in a retry loop; on repeated failure it gives up with (binaryninja.txt
    ~line 15121-15148):
        "Fatal Error: Tried 5 times to send command '<cmd>' to <instrument>.
         PROGRAM ENDING."
    (title "IMT LampElectrical Probing") - i.e. 5 attempts, then the whole app
    exits. This is NOT implemented as a hard-exit in Lampexe's simulated run.
  - Bus errors are logged to C:\ProbeData\HPIB_Bus_Errors.txt (line 15772).

2. ELECTROGLAS 2001X PROBER (control: HPIB_2001X)
======================================================================
Command format: "SP" + a mode/axis digit + "X" + x-coordinate + "Y" + y-coordinate
("Stage Position", presumably). Two literal forms were found verbatim:

  SP2X0Y0     - move to the align/reference site (X=0,Y=0) - used before
                confirming alignment with the operator (binaryninja.txt:4645, 8542)
  SP1X        - sent during Form_Load / initial prober configuration
                (binaryninja.txt:11542) - exact trailing arguments not resolved

  Per-die moves during the actual probe run build the same "SPnXxYy" shape
  dynamically with each die's real coordinates (the app just concatenates the
  numbers at runtime, so there's no fixed literal string to recover for those -
  only the pattern is confirmed, not the exact digit-formatting/precision).

  Expected reply: "MC" (Move Complete). Any other reply triggers:
        "Prober command '<cmd>' failed to return 'MC', instead said:
         <reply>
         Continue anyway?"
  (Yes/No dialog - confirmed at 5 separate call sites: 4644-4662, 6451-6470,
  6664-6682, 8235-8254, 8541-8559, 8963-8981 - the operator can choose to
  proceed even after a failed/unexpected reply.)

4. RELAY/SWITCH UNIT (control: HPIB_Relay1) - revised, was "NOT FOUND"
======================================================================
The previous version of this file said no relay command string could be
found anywhere. That was true for all 4 decompiler outputs - it stopped being
true once the actual exe was available to search directly. None of this is
traced through control flow (no decompiler reached it), but the strings and
their byte-offset clustering in the binary are strong, consistent evidence:

  CLOSE <channel>              - closes (connects) a relay channel
  OPEN <channel>                - opens (disconnects) a relay channel
  (both have a trailing space in the binary, i.e. built the same way as the
  Keithley's "sour:volt " etc. - a fixed prefix with a channel name appended)

  Channel names found: RELAY1, RELAY2, RELAY3, RELAY4, RELAY5

  Byte-offset clustering in the exe is informative here: RELAY1/RELAY3/
  RELAY4/RELAY5 sit immediately next to FET1/FET2/FET3/FET4 (all 8 strings
  within ~70 bytes of each other), while RELAY2 sits apart, right next to
  CLOSE/OPEN/READ? instead. Combined with a DB query found nearby -
  "SELECT * FROM tblInstruments WHERE tblInstruments.fldIsLampElectrical =
  true" immediately followed by a "Set Instrument '<name>'" status-message
  template - the likely picture is: this app tests multiple electrical test
  structures (FET1-4, or similar) AT EACH PHYSICAL PROBE POSITION, not one
  measurement per touchdown. tblInstruments supplies the list (name + which
  relay channel routes to it), the app logs "Set Instrument '<name>'", sends
  CLOSE/OPEN on the matching RELAY channel, then runs the Keithley sequence
  from section 3. RELAY2 being the odd one out is consistent with it being a
  shared/common or ground-reference channel rather than a per-FET one, but
  that's inference, not confirmed.

  IMPORTANT CORRECTION (2026-07-22, after reading the real tblInstruments):
  this app has exactly ONE relay GPIB address, not five - RELAY1 at
  GPIB0::9::15, fldIsLampElectrical=True (section 0.5). RELAY2/RELAY3
  (::12/::14) are real instruments on the same bus but confirmed NOT used
  by this app; RELAY4/RELAY5/FET1-4 don't appear in this app's real
  tblInstruments at all (they were from the user's second, explicitly-
  caveated "may not fully apply to this prober" reference table - section
  0.6). The cleaner reading: HPIB_Relay1 is ONE physical card (an
  E1345A/E1351A-class 16-channel multiplexer, per section 0.6's product
  identification) at one GPIB address, and the CLOSE <channel>/OPEN
  <channel> commands select a channel WITHIN that one card (a
  "FET1"-style channel label, not a separate GPIB address) - this fits the
  real flush-file evidence (section 0.8) exactly: fldSwitch cycles 1,2,3,4
  per quad, i.e. 4 channel selections on the one relay card, one per
  co-probed die.

  This reframes comboDies (frmRunTime, Engineering Mode frame, ~35 AddItem

  Status text: "Initializing Switches" (parallel to the other two

4.5. PHYSICAL MODEL: 4 dies/shot, 8 probe card pins (user-supplied, 2026-07-22)
======================================================================
None of this is in the exe - checked directly (grepped the full disassembly,
recstudio.txt/snowman.txt/reko.txt, every .frm/.bas file, and the exe's own
raw string table for "pin" - zero genuine hits anywhere). This is domain
knowledge from the user, not reverse-engineered, and it's what makes sense of
section 4's relay/FET findings:

  - One probe touchdown ("shot") mechanically contacts 4 dies at once (a 2x2
    quad), via 8 probe card pins total -> 2 pins per die.
  - This independently matches what the *other* half of this reverse-
    engineering effort already established from the recipe-generator .xls/
    VBA side, completely separately (see the lamp-pma-vs-recipe-generator
    memory note): LaMP's MajorMoves sheet packs dies into the exe's .PMA
    files in exactly this same 2x2-quad arrangement. Two independent traces
    - one from Excel macro analysis, one from exe disassembly - landing on
    the same "4 dies per physical move" structure is a good consistency
    check that neither is a fluke.
  - This explains why FET1-4 need their own relay channels despite a single
    touchdown: even though all 4 dies are mechanically contacted
    simultaneously, only ONE die's pins can be electrically connected to the
    Keithley's Force/Sense lines at a time (a single 2-wire SMU can't measure
    4 separate devices at once) - so the relay multiplexes between them:
    CLOSE the channel for die N's FET, run the Keithley SCPI sequence +
    READ?, OPEN it, move to die N+1's channel, repeat. 4 FETs x 2 pins each
    = 8 pins, matching RELAY1/RELAY3/RELAY4/RELAY5 mapping one-per-die (the
    exact channel<->die-position order isn't confirmed, just that there are
    4 of them for 4 dies). RELAY2's separate clustering (section 4) is
    consistent with it being the 9th/shared connection - e.g. a common
    Low/ground line tied across all 4 dies' second pin, rather than a 5th
    per-die channel, though this specific detail is still inference.
  - This is also consistent with tblLampElectricalMeasurements having both
    fldDieID and fldSwitch as separate columns (section 3/4's DB schema
    notes) - one row per (die, switch-state) combination within a single
    shot, not one row per shot.
